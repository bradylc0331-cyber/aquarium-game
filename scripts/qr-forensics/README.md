# QR 讀不到——鑑識腳本

2026-09-02 追「實機 QR 一直讀不到」時寫的。全部**離線**跑，吃的是
`scripts/qr-dump.js --camera=C270` 存在 `output/qr-dump/` 的
`frame.png`、`warped.png`、`report.json`，所以不需要接攝影機也能重現。

```bash
node scripts/qr-dump.js --camera=C270      # 先在有鏡頭的機器上抓一次資料
node scripts/qr-forensics/find-finders.js  # 之後都可以離線重跑
```

| 腳本 | 回答什麼 |
| --- | --- |
| `offline-search.js` | 把偏移搜尋放大到 ±16px 並掃描模組尺度，找 QR 到底在哪 |
| `find-finders.js` | 直接在校正後畫面找三個定位圖案，量出 QR 真正的位置／尺度／旋轉 |
| `verify-fix.js` | 用定位圖案建立取樣格線再比對，驗證修法有效（含局部微調） |
| `frame-straightness.js` | 量印在紙上的引導框彎不彎，分辨光學變形與印偏 |
| `marker-shape.js` | 量四個黑方塊在校正後的外框（註：下方兩塊會被陰影汙染，數字不可盡信） |

2026-09-02 的結論（用約拿那張紙、C270、1280x960）：

- 相機**拍得到**清楚的 QR，原始畫面上每個模組 3.69px，不是失焦也不是太小。
- QR 實際落點比 `QR_AREA` 假設的位置偏 **(+7.2, +5.0)** canonical px，
  垂直方向還被壓縮約 8%；`qrCode.js` 的 `SEARCH_OFFSETS` 最遠只到 ±3.0px，
  所以永遠搜不到 —— 七個人物的分數才會全部擠在 0.42~0.46（亂猜是 0.5）。
- 改用定位圖案建立格線：分數 0.42 → **0.063**；再加小範圍微調 → **0.016**。
- **已修**（2026-09-02）：`src/qrCode.js` 的 `identify()` 改成先 `locateFinders()`
  找三個定位圖案來張格線，找不到才退回原本的固定位置＋`SEARCH_OFFSETS`。
  拿這張實機照片跑產品的 `identify()`：`jonah score 0.066`、1.8ms。
  測試在 `test/qrCode.test.js` 最後四條，用的就是這裡量到的 (+7.2, +5.0) 與 0.92 倍。
- **實機確認**（2026-09-02 晚，C270、約拿那張紙）：`identify()` 回傳
  `jonah score 0.039`。同一張紙換個位置擺，定位圖案落在 (388.6, 29.9)，
  比第一次的 (390.3, 31.1) 少偏 1.7px —— 偏移**主要是系統性的**（兩次都 +5~+7px），
  但會隨擺放變動 1~2px。所以不是單純印偏（那會固定不變），
  也不是隨機誤差（那不會每次都往同一個方向偏）。要定案還是得做
  「同一張紙轉 180° 再量」那個測試。

## 另一個被這件事帶出來的 bug（已修）

`control.html` 的 outline overlay 把「原本就透明」的像素當成「最濃的線條」，
於是 `WORK_AREA` 以外整片被塗成不透明深藍，蓋住 QR 區與四個定位方塊。
產品的 `identify()` 吃的是乾淨的 `warped`，所以功能沒壞，但
**預覽畫布看不到 QR**，而 `qr-diagnose.js` 正好讀那張畫布 ——
連續兩輪把「QR 讀不到」誤診成「反光／照明不足」就是這麼來的。
現在 `qr-diagnose.js` 自己算 warp，不再讀預覽畫布。
- 位移的成因**還沒定案**。框內的直線只彎約 2px，光學變形不足以解釋 7px；
  QR 又剛好跨在四個方塊圍出的範圍之外（y 8~78，上方方塊中心在 y=32），
  紙前緣沒完全貼平是目前最合理的猜測。判別方法：把紙壓平、或轉 180° 再
  `qr-dump` 一次 —— 偏移會變就是幾何（翹起／光學），不變就是印出來就偏。
